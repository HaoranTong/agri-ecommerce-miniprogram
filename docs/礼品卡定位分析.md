**礼品卡定位**

- 已完整阅读 [功能规格及技术架构说明书_v1.0.md](vscode-file://vscode-app/e:/DEV_TOOLS/Microsoft VS Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html)，其中“虚拟购物卡”章节与您刚才的描述保持一致：卡片既可以是“储值卡”也可以是“商品兑换卡”，兑换人需重新填写收货信息，购卡人与收卡人完全解耦。
- 核心需求不是简单金额抵扣，而是“订单完成后生成卡 → 受赠人凭卡兑换指定 SKU／组合包”，也支持多件套与 0 元换货。
- 分享方式需同时支持 `digital_share`（社交链接/二维码 + PIN）和 `printable`（可打印 PDF/PNG，二维码直达兑换页，仍需 PIN 验证），以满足“线上无痕赠礼”和“实体卡交付”两类场景。
- PIN 必须一次性展示（或二次验证后重新展示），并通过 `wp_myshop_gift_cards` + `wp_myshop_gift_card_redemptions` 表记录分享、领取、核销的全链路。

**业务流程梳理（结合文档 + 需求）**

- **下单阶段**：在商品下单页或独立“购买礼品卡”入口，让用户选择“直接发货”还是“生成购物卡”；若选择购物卡，需要绑定礼品卡模板（储值或绑定 SKU）并跳过收货地址。
- **发卡阶段**：订单状态进入 `wc-completed` 触发卡号/PIN 生成，落表 `wp_myshop_gift_cards`，同时给购卡人提供一次性查看/下载入口。
- **分享阶段**：购卡人可选 `digital_share`（生成 share_token、带参数二维码/链接、可设渠道）或 `printable`（生成含二维码+遮挡 PIN 的图档）。
- **领取阶段**：受赠人通过链接/扫码到达 [/pages/giftcard/claim](vscode-file://vscode-app/e:/DEV_TOOLS/Microsoft VS Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html)，输入卡号+PIN 完成 [bind_status=bound](vscode-file://vscode-app/e:/DEV_TOOLS/Microsoft VS Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html)，系统清空 share_token，防止再次领取。
- **兑换阶段**：
  1. 商品兑换卡：调用 [/gift-cards/redeem](vscode-file://vscode-app/e:/DEV_TOOLS/Microsoft VS Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html)，后端创建 0 元订单、锁定 SKU，卡状态改为 `redeemed`。
  2. 储值卡：在常规下单时选择“使用购物卡”，按余额抵扣，多次使用时写 `wp_myshop_gift_card_redemptions` 日志。
- **审计与异常**：购卡人和运营后台可查看分享/领取/核销日志；支持锁卡、重置 PIN、重新生成分享包等运维动作。

- **后台入口现状**：myshop-core 目前只提供 API（`/gift-cards/templates`）没有可视化界面；若要配置模板，需要先在 WordPress 后台开发一个「礼品卡模板」菜单或用 PHPMyAdmin 直接写入 `wp_myshop_gift_card_templates`。
- **“所有商品都可出礼品卡”**：如果改成“每个订单都自带礼品卡选项”，确实可以绕过模板表，但模板里包含有效期/配送方式/PIN 策略等配置，完全去掉模板会导致这些策略散落在订单层，不利于后续维护。更可行的是：保留模板表，但允许为每个商品/组合自动生成一个默认模板（可通过批量脚本创建），下单时勾选“生成礼品卡”即可引用对应模板；这样后台仍有配置入口，而前台体验也统一。
- **“礼品卡=延迟发货”模式**：把礼品卡视为“订单延迟发货”的凭证在逻辑上可行：
  1. 用户下单选择“礼品卡交付”→ 订单立即生成但不发货。
  2. 系统创建礼品卡并绑定该订单的 SKU/数量。
  3. 受赠人兑换时触发“发货通知”，系统以原订单或新 0 元订单形式安排发货。
     这种模式仍建议借助模板来记录“每张卡包含哪些 SKU/数量、有效期、可否重复兑换”等规则，否则后续要修改某个礼品卡属性需要逐单改动。
- **储值卡与积分**：把储值卡做成“一种特殊积分”理论上可简化实现（毕竟积分账本已有），但文档明确要求储值卡/商品卡支持独立的分享、打印、防伪、PIN、核销日志，如果把它混入积分账户就无法区分“谁送给谁”“送礼过程无痕”“部分抵扣+日志”等关键诉求。此外，积分通常可叠加活动抽奖等行为奖励，和“真实订单金额”在风控上不同，混合后会让财务与用户体验混淆。可以考虑：储值卡兑换时向积分系统写一条“特殊积分”记录用于对账，但不要用积分余额作为唯一数据源。
- **推荐方案**：
  1. 在后台新增礼品卡模板管理界面（字段来自 `wp_myshop_gift_card_templates`），支持“商品兑换”“组合套装”“储值卡”三类模板。
  2. 下单页面提供“发货/礼品卡”选项；若选礼品卡，前端根据商品 ID 自动匹配模板（若找不到就提示“请联系运营创建模板”）。
  3. 实物礼品卡（打印）与数字分享共用一套模板，只是 [delivery_modes](vscode-file://vscode-app/e:/DEV_TOOLS/Microsoft VS Code/resources/app/out/vs/code/electron-browser/workbench/workbench.html) 不同。
  4. 储值卡仍使用模板控制面值/可用场景；若需要与积分互通，可在兑换时写入积分流水，但不要直接当积分余额。

这样既保留用户希望的“任意组合都可礼品卡交付”，也不破坏已有的模板/日志/审计机制，后续要做批量促销、礼盒套装或打印实体卡都更容易扩展。

- **后台模板管理插件页**

- **订单→礼品卡生成链路**
  - WooCommerce 端添加 checkout 选项（`woocommerce_after_order_notes`）：“此订单以礼品卡形式交付”。若勾选，则生成订单元数据 `delivery_method = gift_card`。
  - 下单时根据购物车商品集合匹配模板：优先精确 SKU 模板，其次分类/默认模板，找不到则提示“该组合暂不支持礼品卡”。匹配到模板后写入订单 meta（模板 ID、期望交付方式）。
  - 在订单转入 `wc-completed` 的钩子（`woocommerce_order_status_completed`）里：读取订单 meta → 生成礼品卡记录（卡号、PIN、快照、有效期），调用既有 share/pin 逻辑，并给购卡人发送邮件/站内通知（含卡号查看入口）。
  - 若模板类型为 `custom_bundle`，会把订单行项目 JSON 存入 `bundle_config`，兑换时据此生成发货单（0 元订单或通知原订单发货）。
